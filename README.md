# تحديث v2 — معالجة انعدام التكات وتشخيص التغذية

## تحديث Render دون تغيير أسرارك
استبدل ملفات المشروع في المستودع ثم Deploy. أبقِ RADAR_BOT_TOKEN وADMIN_TELEGRAM_ID وPO_SSID وPO_WS_URL كما هي إن كانت تعمل في المصادقة.
أضف متغيرين (ولهما نفس القيم افتراضياً حتى لو لم تضفهما):
```
PO_TIMESTAMP_OFFSET_SECONDS=auto
PO_SUBSCRIPTION_MODE=browser
```
أمر التشغيل ما زال `python -u bot.py`. سطر التحقق: `build=v2-feed-fix`.

افتح /start ثم الحالة. يجب أن تظهر تكات مقبولة أكبر من صفر وعدد أزواج حديثة أكبر من صفر، وليس مجرد اتصال مصادق. انتظر فترة التهيئة بعد وصول أول تكات: نحو 3 دقائق للسريع و10 دقائق للدقائق. لا تبدأ حساب فترة التهيئة من لحظة تشغيل الخدمة إذا لم تكن الأسعار تصل بعد.

## ما أصلحناه فعلياً
1. النسخة v1 ترسل subscribeSymbol فقط. النمط browser يرسل أيضاً changeSymbol لكل زوج وتهيئة قراءة indicator/load وfavorite/load وprice-alert/load. لا يرسل أوامر تداول أو تعديل حساب/مال. النمط subscribe_only متاح للمقارنة إذا كانت المنصة تقيّد تعدد تغيير الأصل؛ لا يضمن أي نمط قبول 32 اشتراكاً من المنصة.
2. النسخة v1 ترفض أي سعر وقته أكثر من 3 ثوانٍ في المستقبل. المرجع غير الرسمي المُراجع يستخدم TIMESTAMP_OFFSET=-7200 لتطبيع ساعة الأسعار. AUTO يقبل UTC مباشرة، أو فارق UTC+2 بعد التحقق لكل زوج من 3 وصولات متتابعة يمتد وقتها ووصولها ثانية واحدة على الأقل. لا تُطرح ساعتان من كل الأسعار عشوائياً، ولا يُستبدل وقت السوق بوقت الوصول. لا تُقبل فروق عشوائية أو بيانات قديمة بعد التطبيع. يمكن اختيار 0 يدوياً لرفض أي تصحيح، أو -7200 عند تأكدك من تنسيق خادمك.
3. فك binary JSON ومرفقات Socket.IO المتعددة، وJSON النصي داخل updateStream. لا تحويل لأحداث التاريخ إلى أسعار حية.
4. رسائل حالة وتشخيص تميّز مصادقة الاتصال من توافر تكات حقيقية. عدّادات للرسائل، صفوف الأسعار، المقبول والمرفوض وأسباب الرفض وإزاحة الساعة. لا طباعة للجلسات أو الرصيد أو raw frames.
5. تهيئة الاشتراك مجدداً مرة واحدة إن لم تصل أسعار، قبل إعادة الاتصال. heartbeat Engine.IO مع ps للتطبيق. إعادة الاتصال تبقى تلقائية.
6. قواعد تحليل السوق والأصول والمدة والحماية لم تتغير. لا صفقات ولا بيانات محاكاة وقت التشغيل.

## أكواد التشخيص
- WAITING_QUOTES: المصادقة تمت وننتظر الأسعار.
- LIVE_QUOTES: استُقبلت تكات مقبولة في هذه الجلسة؛ العدد الحديث في الحالة هو الفيصل لحداثة الأسعار.
- NO_STREAM_EVENTS: لم يصل حدث updateStream؛ تُراجع تهيئة الاشتراك/الخادم/صلاحية التغذية.
- STREAM_FORMAT_UNSUPPORTED: وصل updateStream لكن صيغته لم تنتج صفوف أسعار مفهومة.
- QUOTE_CLOCK_UNSUPPORTED: وصلت أسعار بفارق زمني لا يدعمه AUTO؛ لا تُلغِ حارس البيانات القديمة. قارن وقت الخادم الفعلي قبل اختيار إزاحة يدوية.
- QUOTES_REJECTED: وصلت صفوف لكن رُفضت؛ أسباب الرفض مفصلة في الحالة (رقم غير صالح، رمز غير مدعوم، تكرار، تقدم/تأخر وقت).
- STREAM_STALE: توقفت الأسعار المقبولة.
- AUTH_REJECTED: رفض مصادقة؛ راجع إطار الجلسة والخادم المتطابقين.

التشخيص في السجل كل نحو 15 ثانية؛ زر الحالة يعرض الأرقام أيضاً. العدّادات الخاصة بالتغذية تعاد لكل اتصال، وتبقى صورة التشخيص الأخيرة أثناء فترة إعادة المحاولة. رموز خارج قائمة الفوركس لا تُضاف تلقائياً ولا تُسمى أزواجاً متاحة.

## حدود التحقق
سجل المستخدم يثبت انعدام التكات المقبولة، لكنه لا يحتوي raw updateStream ولا عدّادات v2، لذلك لا يثبت وحده هل السبب الفعلي ساعة الأسعار أو تهيئة الاشتراك أو صيغة الرسائل أو قيد المنصة. أُصلحت المسارات المثبتة في الكود واختُبرت بمحاكاة محلية، لا اتصال حي بحساب المستخدم. لا ندّعي ضمان قبول الاشتراكات أو حل قيود Render/المنصة عن بُعد.

مراجع البروتوكول التي راجعنا كودها (غير رسمية):
- https://github.com/lordralinc/pocket_option/blob/main/pocket_option/constants.py
- https://github.com/lordralinc/pocket_option/blob/main/pocket_option/utils.py
- https://github.com/lordralinc/pocket_option/blob/main/pocket_option/contrib/default_init.py

أُعيد تضمين اختبارات المصدر تحت tests/؛ نفذ:
```
python -m unittest discover -s tests -v
```
نجح 63 اختباراً محلياً قبل التغليف. منها إعادة إنتاج رفض v1 لأسعار بفارق ساعتين ثم قبولها بعد التطبيع المتحقق، وخادم محاكاة لا يبث حتى changeSymbol، وصيغ المرفقات ورفض البيانات القديمة وحراسة أوامر القراءة فقط. هذه اختبارات صحة الكود وليست شهادة دقة تنبؤية أو تجربة حية.

## الدليل الأساسي (تفاصيل v1؛ تحديث v2 أعلاه له الأولوية)

# Abood Market Radar — رادار عبود للأسواق

مشروع مستقل للقراءة فقط. لا يستورد أو يعدّل روبوت التداول، ولا يحتوي على إرسال أوامر فتح صفقة أو مضاعفات أو وصول إلى MongoDB الخاصة به. الاسم مبني على الاسم المتفق عليه Abood Market Radar.

## ما الذي تم تسليمه؟
- aiogram 3: واجهة عربية، زرا 5–30 ثانية و1–5 دقائق، حالة البث، شرح المنهج، وتصدير آخر تقرير CSV.
- اتصال Pocket Option مستمر مع Engine.IO heartbeat وSocket.IO JSON وbinary attachments، إعادة اتصال بتراجع تدريجي واشتراك منفصل لكل رمز.
- 32 رمز فوركس OTC مطابقة لقائمة assets في الملف المرفق. لا أسهم أو سلع. القائمة ليست وعداً بتوافر جميع الرموز؛ لا يُعتمد أي رمز بلا تكات حديثة منه. لم ننسخ أي أسرار أو جلسات من الأرشيف.
- أسواق حقيقية من البث فقط؛ لا random prices، لا أسعار اصطناعية، لا نسب نجاح مولدة.
- حماية ADMIN_TELEGRAM_ID وقبول التفاعل في المحادثة الخاصة فقط.

## تشغيل محلي
Python 3.12 موصى به:
```
pip install -r requirements.txt
cp .env.example .env
python bot.py
```
عدّل `.env` قبل التشغيل. في Windows انسخ الملف يدوياً. أنشئ بوتاً جديداً عبر https://t.me/BotFather وضع التوكن في RADAR_BOT_TOKEN. استخدم ADMIN_TELEGRAM_ID الخاص بك. **لا تستخدم توكن بوت التحكم القديم** لأن تشغيل polling مزدوج لنفس البوت يسبب تعارضاً.

انسخ إطار المصادقة العامل لديك بالكامل إلى PO_SSID، بما فيه session وuid وisDemo وplatform. لا ترسل أسرارك في الشات أو ترفعها إلى Git. الرابط في PO_WS_URL يجب أن يطابق الخادم والجلسة اللذين يعملان لديك؛ لا نحول REAL إلى DEMO أو العكس تلقائياً. يُفضل الحساب التجريبي للقراءة. قد يؤدي استخدام الجلسة نفسها عبر عدة برامج إلى قيود اتصال تعتمد على المنصة؛ لا توجد ضمانات لتعدد الاشتراكات أو استقرار واجهة غير رسمية.

## Render — مشروع جديد منفصل
1. ارفع **محتويات هذا المجلد** إلى مستودع خاص جديد، وليس إلى مجلد روبوت التداول السابق.
2. أنشئ Web Service جديداً، Python، Build: `pip install -r requirements.txt`، Start: `python -u bot.py`.
3. أضف RADAR_BOT_TOKEN وADMIN_TELEGRAM_ID وPO_SSID وPO_WS_URL في Environment. في لوحة Render لا تضف علامات الاقتباس الخارجية لقيمة PO_SSID؛ الصيغة تبدأ 42[. يمكن استعمال Secret File باسم `.env`؛ يقرأ البرنامج `/etc/secrets/.env` أيضاً.
4. deploy. `/health` فحص حياة فقط ويعود 200 حتى لو فقدت تغذية السوق؛ `/ready` يرجع 503 حين لا توجد تكات حية. لا تجعل readiness شرط restart كي لا تقع في حلقة إعادة تشغيل أثناء تعطل المنصة.
5. ابدأ من /start في البوت الجديد. زر الحالة يوضح عدد الأزواج ذات التكات الحديثة مقابل 32 وعدد الاشتراكات المرسلة (ليس قبولها).
6. `render.yaml` مرفق مع خطة starter المدفوعة؛ راجع سعرها في Render قبل إنشاء الخدمة. لم يُنشأ حساب أو مورد مدفوع نيابة عنك.

للتشغيل المتواصل اختر compute مدفوعاً. المجاني قد يدخل السكون بعد 15 دقيقة بلا حركة واردة، ولا يضمن الاستمرار أو مهلة الدقيقة. لا يوجد ping ذاتي يزعم ضمان منع السكون.
المصدر: https://render.com/docs/free

## زمن الفحص والتهيئة
SCAN_SECONDS=20: انتظار جماعي واحد يجمع تكات إضافية، ثم تحليل الذاكرة مباشرة لجميع الأزواج، وليس 20 ثانية لكل زوج. يُقبل بين 1 و50 ثانية؛ قيمة 20 موصى بها. في الظروف العادية يكتمل الحساب بعد مهلة الفحص مباشرة؛ انقطاع Telegram أو بطء الاستضافة/الشبكة قد يؤخر تسليم الرسالة، لذلك الدقيقة ليست SLA مضموناً.

بيانات الذاكرة لا تُحفظ عند restart. الأفق السريع يحتاج نحو 3 دقائق من البيانات، وأفق الدقائق نحو 10 دقائق (بما فيها نافذة حديثة وخط أساس منفصل). قبل ذلك يصل التقرير نفسه وفيه «بيانات غير كافية»؛ لا نستخدم البيانات القليلة لإنتاج لون أخضر.

نحتفظ بحد 30000 تكة/زوج وبحد زمني 900 ثانية. إذا كان معدل التكات عالياً جداً فقد يملأ الحد العددي قبل الزمن المطلوب؛ النتيجة تبقى غير كافية. TICK_CAPACITY قابلة للرفع حتى 100000 مع مراعاة ذاكرة الاستضافة. بعد كل إعادة اتصال تُفرّغ البيانات حتى لا نخلط جلستين أو نجسر فجوة انقطاع.

## المنهج: وصف قابل للفحص وليس توقع ربح
- سريع: إغلاق آخر تكة بكل ثانية، نافذة حديثة 60 ثانية وخط أساس سابق منفصل من فترة إجمالية 180 ثانية.
- دقائق: عينات 5 ثوانٍ، نافذة حديثة 300 ثانية وخط أساس سابق من فترة إجمالية 600 ثانية.
- العوائد اللوغاريتمية تُحسب فقط بين حاويات زمنية متجاورة. لا forward fill ولا حقن بيانات تاريخية.
- تقاس نسبة RMS للتذبذب إلى خط الأساس، نسبة القفزات بعتبة robust تعتمد MAD وRMS، كثافة انعكاس الاتجاه، وكفاءة المسار |صافي التغير|/مجموع التغيرات المطلقة.
- لا مقارنة رقم سعر زوج برقم زوج آخر؛ المقارنة مع أساس الزوج نفسه.
- حراس جودة: حداثة وقت السيرفر والوصول، تغطية >=80%، فجوات لا تتجاوز ثلاث وحدات عينة، ورفض أسعار غير منتهية أو سالبة أو رسائل قديمة/خارج الترتيب. افحص مزامنة ساعة الجهاز إن رُفضت التكات.
- سلسلة ثابتة تماماً لا تُسمى مستقرة بل غير قابلة للتقييم؛ قد تكون تغذية ساكنة أو سوقاً قليل الحركة.

حدود مبدئية واضحة في analysis.py:
أحمر إذا spike_fraction>=.05 أو volatility_ratio>=2.5 أو (reversals>=.65 وefficiency<.15).
أخضر إذا ratio<=1.5 وspikes<=.02 وreversals<=.4 وefficiency>=.2.
أصفر خلاف ذلك، وأبيض عند نقص الجودة.
هذه الحدود **غير معايرة على نتائج حية** ولا تعني دقة تداول مثبتة. لا يوجد «نسبة نجاح» ولا احتمالية ربح ولا توصية UP/DOWN. انتظام قوي باتجاه ما لا يجعله صالحاً لاستراتيجية عكس الاتجاه، وانخفاض التذبذب لا يضمن سلامة الصفقة. اللون الأحمر قد يصف اضطراباً مناسباً لبعض الاستراتيجيات لكنه ليس حكماً مطلقاً على السوق.

## تشخيص
AUTH_REJECTED: جدّد SSID من المنصة وتحقق من الخادم المطابق.
CONNECT_TIMEOUT / WS_DISCONNECTED: اتصال أو حظر/قيود مركز بيانات ممكنة؛ لا يمكن الجزم بالسبب من هذا الكود وحده. جرّب نفس الجلسة محلياً وقارن بالتوقيت نفسه. تغيير منطقة الاستضافة تجربة، لا إصلاح مضمون.
NO_LIVE_TICKS: المصادقة/الاتصال لم يوفرا تكات. يكرر الاتصال تلقائياً دون إنتاج نتائج زائفة.
عدد أزواج أقل من 32: قد تكون بعض الرموز غير متاحة أو غير مشتركة فعلياً أو حد المنصة لا يسمح بالكل. يعرض النقص بوضوح ولا يدعي مسحاً كاملاً ناجحاً.
إذا تغيّرت صيغة updateStream، يلزم تحديث protocol.py وفق عينة منزوعة الأسرار. لا تسجل raw frames أو التوكنات.
توقف polling بعد Redeploy: تأكد أن نسخة واحدة فقط تستخدم توكن الرادار. لا تعطل بوت التداول القديم؛ استخدم توكناً جديداً.
